= Conformance Tooling — Administrator / Developer Configuration Reference
:toc: left
:toclevels: 3
:sectnums:

This document covers all configuration options for the conformance data generation (`conformance-data`) and conformance specification generation (`conformance-guide`) tools. It is intended for administrators and developers who need to customize generation behavior.

For an overview of what the tools produce, how to work with the conformance YAML, and how the merge process works, see the link:partYY-conformance-user.adoc[End-User Guide].

== Conformance Data (`conformance-data`) Configuration

The `conformance-data` tool has a small set of internal defaults. Configuration can be provided via `--config` files (YAML or JSON).

=== Running the Tool

[source,bash]
----
# Initial generation (no previous file exists)
conformance-data --openapi api.yaml --output conformance.yaml --target-directory documentation/conformance

# With rules for resource ordering and metadata
conformance-data --openapi api.yaml --rules rules.yaml --output conformance.yaml --target-directory documentation/conformance

# Merge with existing conformance (automatic when --previous is provided)
conformance-data --openapi api.yaml --rules rules.yaml --previous documentation/conformance/conformance.yaml --output conformance.yaml --target-directory documentation/conformance

# With configuration file(s)
conformance-data --openapi api.yaml --rules rules.yaml --previous conformance.yaml --output conformance.yaml -c config.yaml
----

=== Update Control (`updateConformanceYaml`)

This is the key safety setting. When `false` (the default), the tool performs the merge and reports what would change but does *not* modify the conformance YAML file on disk.

Set in your config file:

[source,yaml]
----
updateConformanceYaml: true
----

When multiple config files are passed, the last value wins.

The tool's CLI output changes based on this setting:

* *Disabled* — shows "Changes that would be applied" as a diff summary
* *Enabled* — shows "Changes applied" confirming the write

=== Merge Engine Details

The merge engine (`merge-engine.ts`) implements the following algorithm:

. Start with the generated document as the base structure (reflects current OAS)
. Carry forward human-edited `condition`, `comment`, and `rule` values from the previous conformance
. Mark new elements with `x-added: <version>`
. Record removed elements in `x-removed` under the new version key
. Preserve historical `x-added` and `x-removed` from the previous document
. Filter stale `x-removed` entries for paths that now exist in generated output (reconciliation)

==== Comment Classification

Comments are classified into three categories during merge:

* *Auto-generated* — starts with `One of:`, `Any of:`, or `Present in subclasses:` followed by bullet items only; fully regenerated each run
* *Manual* — does not start with a known prefix; fully preserved
* *Mixed* — starts with an auto-generated prefix but has additional text after the bullet items; the prefix portion is regenerated while the manual portion is preserved and appended

==== Condition Carry-Forward Logic

[cols="2,2,3"]
|===
| Previous | Generated | Result

| Empty
| Any
| Generated value used

| `M`
| `M`
| Agree — no change

| Non-M (non-empty)
| Same
| Agree — no change

| Non-M (non-empty)
| Different (not M)
| Previous carried forward (human judgment, with warning)

| Any (not M)
| `M`
| New mandatory takes precedence (with warning)
|===

=== Schema Validation

The input conformance YAML is validated against `tmf.conformance.v1.schema.json` using Ajv before processing. The schema enforces:

* Resource names must start with uppercase: `^[A-Z][A-Za-z0-9]+`
* Attribute paths follow the pattern: `^(@[a-zA-Z_]\w*|[a-zA-Z_]\w*(\.[a-zA-Z_]\w*)*(\.@[\w]+)?)$`
* Operations are limited to: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`
* `operations-details` supports `POST` (with `mandatory` and `discriminators`) and `PATCH` (with `patchable`, `non-patchable`, and `discriminators`)
* Each discriminator subtype in POST has `mandatory`; in PATCH has `patchable` and `non-patchable`

=== Diff Summary

When `updateConformanceYaml` is `false` and a previous file exists, the tool computes and displays a diff summary showing added and removed paths. This is useful for CI pipelines to detect drift.

=== x-removed Path Summarization

When many entries share a common parent path, they are summarized for display (threshold: 5 entries under the same parent):

[source,text]
----
Widget.attributes (3 entries)     # Instead of listing each attribute
Gadget.operations.PUT             # Single entries shown individually
----

== Conformance Specification (`conformance-guide`) Configuration

The `conformance-guide` tool ships with defaults in `config/defaults.yaml`. Override settings by passing one or more `--config` files.

=== Running the Tool

[source,bash]
----
conformance-guide \
  --openapi api.yaml \
  --conformance documentation/conformance/conformance.yaml \
  --generated-target-directory documentation/conformance/generated \
  --target-directory documentation/conformance/target \
  --output conformance.adoc \
  --rules rules.yaml \
  -c config.yaml
----

=== Resource Ordering

The `resourceOrder` setting controls how resources appear in the generated document:

* *`rules`* (default) — ordered per the rules YAML file. Discriminator subtypes are inserted after their parent.
* *`alphabetical`* — all resources sorted alphabetically
* *`alphabetical-grouped`* — sorted alphabetically but with discriminator subtypes grouped after their parent

=== Parts Processing (`processConformanceParts`)

When `false` (the default), the generator preserves existing operation part files in `target/parts/` and does not modify them. This allows manual edits to part files to persist.

When `true`, the generator actively manages part files:

* Copies and numbers operation files based on which operations have mandatory resources
* Removes operation files for operations without mandatory resources (when `removeSectionsForOptionalOperations: true`)

NOTE: When `removeSectionsForOptionalOperations` is `true`, it overrides `processConformanceParts` and always performs legacy-mode selective file writing.

=== Config File Format

Config files use a mix of direct keys and namespaced keys for backward compatibility:

[source,yaml]
----
# Add extra non-patchable attributes (shallow-merged with defaults)
"conformance.nonPatchable":
  "@type": "@type is immutable"
  "@baseType": "@baseType is immutable"
  "@schemaLocation": "@schemaLocation is immutable"
  "id": "id is server-generated"

# Override IPR mode
"conformance.iprMode": "RF"

# Disable comments column in mandatory operations tables
mandatoryOperationsWithComments: false

# Disable attribute structure deduplication
deduplicateAttributeStructures: false

# Enable/disable conformance YAML write-back
updateConformanceYaml: true

# Resource ordering strategy
resourceOrder: alphabetical-grouped

# Reorder operations (e.g., POST first)
default_conformance:
  layout:
    operations:
      - POST
      - GET
      - PATCH
      - PUT
      - DELETE
----

=== Config File Key Mapping

[cols="2,2,2"]
|===
| Config file key | Internal property | Merge behavior

| `conformance.nonPatchable`
| `nonPatchable`
| Shallow merge (user entries added/overwritten)

| `conformance.iprMode`
| `iprMode`
| Replace

| `mandatoryOperationsWithComments`
| `mandatoryOperationsWithComments`
| Replace

| `deduplicateAttributeStructures`
| `deduplicateAttributeStructures`
| Replace

| `updateConformanceYaml`
| `updateConformanceYaml`
| Replace

| `resourceOrder`
| `resourceOrder`
| Replace

| `processConformanceParts`
| `processConformanceParts`
| Replace

| `default_conformance.layout.operations`
| `operationsOrder`
| Replace
|===

Multiple config files can be passed; they are applied in order (last wins).

=== Pipeline Run Mode

When the `PIPELINE_RUN` environment variable is set to `true`:

* Only the `generated/` folder and metadata in the main document are updated
* The conformance YAML is *not* written back (regardless of `updateConformanceYaml`)
* Useful for CI/CD pipelines where only the rendered output needs refreshing without side effects

=== Custom Templates

Pass `--templates <dir>` to provide a custom template source directory. When specified, the generator uses your templates instead of the embedded ones. Template files are Mustache (`.mustache`) and follow the same naming convention as the defaults.
